# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

GameTimeNext is a Windows-only WPF desktop app (.NET `net10.0-windows`, x64) for tracking game playtime, launching games, and managing profiles/playthroughs. Data is stored locally in SQLite. It succeeds GameTimeX (`../GameTimeX`) and includes a migration path from it (`Core/Application/GTXMigration`).

## Build & checks

The solution references two sibling repositories that must be checked out next to this one (all are in `GameTimeNext.slnx`); the build fails without them: **`../UIX.ViewController.Engine`** and **`../UIXMonitorTweaks`** (switching monitors on/off, primary display, identify overlay, default audio device; used by Screensetups). Much of the base framework (`UIXApplication`, `UIXViewControllerBase`, `UIXTableObjectBase`, `UIXQuery`, `FnString`, `FnLog`, …) lives there, not here.

```bash
dotnet build GameTimeNext.slnx
dotnet run --project GameTimeNext/GameTimeNext.csproj
dotnet run --project GameTimeNext/GameTimeNext.csproj -- minimized   # start hidden, no splash
```

- Code rules check: `python Scripts/cleancode.py` — enforces where certain string literals (`"GameTimeNext"`, `"MaxPra"`, …) and identifiers (`DirectorySeparatorChar`) may appear, with per-file allowed counts. If a new occurrence is legitimate, add it to the allowlist in the script.
- There is no test suite (`GameTimeNext.Tests` contains only build output). `RemoteMonitoring/` and `GameTimeNext.Shared/` are untracked work-in-progress folders and are not in the solution.
- Installer: Inno Setup script at `Installer/GameTimeNext.iss`. Import packages (`GameTimeNext/ImportPackages/*.zip`, created by the module "Create Import Package") are taken by the installer directly from that source folder and installed to `temp\import`; they need no `CopyToOutputDirectory` entry in the csproj. Every zip in the folder is shipped, so remove test packages before a release build.
- App icon: the sources are the SVGs in `Branding/`, one per size range (`icon_16.svg` pixel aligned; `icon_small.svg` for 24/32 px, plain G without tile so it fills the taskbar slot; `icon_medium.svg` for 48/64 px; `icon_large.svg` for 256 px). `powershell -ExecutionPolicy Bypass -File Branding/build_icon.ps1` renders them with headless Edge and writes `GameTimeNext/UI/Ressources/GTN_APP_ICON.ico` (exe, taskbar, installer) and `Branding/logo_1024.png`. Never edit the `.ico` directly: change the SVGs and rerun the script. The mark is a game cover frame forming a "G" (dot top right = start of the playtime line), with T and N built into it from 48 px up; small sizes stay G only because T/N are unreadable there. `UI/Ressources/GTN_CLS_ICON.png` is the CryLoud Studios logo, not the app icon.
- Placeholder cover: `UI/Ressources/GTN_COVER_PLACEHOLDER.png` (600 × 900, preset for new profiles and button "Placeholder" in the profile's Image tab, loaded via `CFProfilesApp.LoadPlaceholderCover`) is rendered from `Branding/cover_placeholder.svg`. Never edit the PNG directly: change the SVG and render it again with headless Edge (`msedge --headless --hide-scrollbars --window-size=600,900 --screenshot=<png> <svg file URL>`). Each profile gets its own copy of the cover, so a new design doesn't change existing profiles. Profile covers are always loaded for display with `CFProfilesApp.LoadProfileCover(PPFN)`, never with `FnImage` directly: a missing or unreadable cover file falls back to the placeholder, so the profile is still shown. The app background (`ProfileCoverBackground`) and the blackout particles (`CFBlackoutParticleCover`) decode the cover themselves and fall back to the placeholder too (`CFProfilesApp.LoadPlaceholderCover` / `OpenPlaceholderCoverStream`).
- Version is set in `GameTimeNext.csproj` (`VersionSemantic`, `VersionTag`, `BuildDate`) only. The installer reads it from the built Release exe (`FileVersion` / `ProductVersion`), so build Release before compiling the installer. Release notes go in `Core/Application/UpdateChanges/UpdateChanges_v*.md` (`_vNEXT.md` for unreleased), written in GitHub Markdown (alerts like `> [!IMPORTANT]` are supported); the csproj includes the folder by wildcard (`Content`, copied to the output), so new files need no csproj entry. The same applies to images in `UI/Ressources/` (`Resource` by wildcard, referenced as pack URIs `/UI/Ressources/...`). They are shown after an update in the CFMBOX (`CFMBOXType.Markdown`, rendered by `UIXMarkdownRenderer` in the engine, `FrameworkElements/Markdown/`); older versions are plain `.txt` (shown as memo text). Start profile "Show changelog vNEXT" (`-showchangelog`) always shows `_vNEXT` to check the result.

## Code rules

From `Scripts/unallowed_code.md` and `.github/copilot-instructions.md`:
- Use `FnString.IsNullEmptyOrWhitespace` instead of `string.IsNullOrWhiteSpace` / `string.IsNullOrEmpty`.
- Use `FnDirectory.EnsureDirectoryExists` instead of `if (!Directory.Exists) Directory.CreateDirectory`.
- Paths/app names come from `AppConfig` (`Core/Framework/Config/AppConfig.Paths.cs`), not hard-coded strings.
- Do not suppress validation on ComboBox `SelectionChanged`; tab validation must run together with field validation/adorner checks.
- XML doc comments: concise, no icons/emojis.
- **`x:Name` in XAML** always starts with the control type as a lowercase prefix, followed by a PascalCase name (e.g. `btnSave`, `txbDescription`, `cmbParam`, `chbPaused`, `lblTitle`). Only `PART_*` names required by WPF control templates are exempt. Existing names with an uppercase prefix (`BtnSave`, `TxbDescription`, …) are legacy and are being renamed; when renaming, also rename the matching `EV_<x:Name>` handlers and all code references.
- All comments in source code (C#, XAML, scripts — in this repo and in `../UIX.ViewController.Engine`) must be in English, even when the conversation is in German.
- **View models only for list entries:** a view model class is only used for the entries of a list (the objects in an `ItemsSource`, e.g. tiles, rows, menu entries), and list templates bind to them. Everything else (texts, visibility, enabled state, single values) is set by the controller directly on the named controls (`GetView().txTitle.Text = ...`, `FnControls.SetVisible(...)`); no view model for a whole view and no bindings of single controls to one. Existing view-wide view models are legacy, not a pattern.
- **No logic in code-behind:** `*.xaml.cs` files contain only `InitializeComponent()`. View logic goes into the module's controller (for `MainWindow`: `MainWindowController`); reusable UI behavior goes into attached properties / helpers in `Core/Framework/UI/`, switched on from XAML or styles. Existing code-behind logic is legacy, not a pattern.
- **Tree grid rows:** the column properties of a `UIXTreeGridRow` subclass start with `CO` (Column) followed by the table / field code (e.g. `CONAME`, `COPTTY`, `COMEDE`); flags that are no column (e.g. `IsFolder`) keep a normal name. The row icon is set with `row.Icon` (glyph, property of `UIXDataGridRow`; font `UIXDataGrid.IconFontFamily`, set to `Font.Icons` by the GTN style): a `UIXTreeGrid` shows it in its tree column (`UIXTreeGridTextColumn`), a plain `UIXDataGrid` in front of the value of a `UIXDataGridTextColumn` (instead of `DataGridTextColumn`, usually the first column).
- **Row colors:** a list row (`UIXDataGridRow`, also tree grid rows) gets its own colors with `RowBackground` / `RowForeground` (null = style default); the GTN row style draws the background below the hover / selection tint and passes the text color to all cells. Take the colors from `FnColor` (`Core/Framework/Utils/FnColor.cs`: application colors of `Colors.xaml` as frozen brushes, e.g. `FnColor.Danger()`, `FnColor.Warning(0x1F)` for a light tint, `FnColor.Get("Color.X")`), usable in any thread (adapters build the rows in `Task.Run`); no `System.Windows.Media.Brushes` (system colors don't fit the theme) and no own copy-and-freeze of resources. FnColor's brushes are snapshots: `FnTheme` clears its cache when the accent colors change, XAML keeps using `DynamicResource`. Row view models notify through the base class (`SetProperty` / `OnPropertyChanged` of `UIXDataGridRow`); don't declare an own `PropertyChanged` in a subclass.
- **Cell values and colors:** text columns of a list row are `UIXDataGridCell` properties, not `string` (`public UIXDataGridCell CONAME { get; set; } = "";`); bool / number columns keep their type. A cell converts implicitly from and to string (`row.CONAME = t1.NAME;`, `string name = row.CONAME;`), is shown by `ToString` and sorted by its text, so columns keep `Binding="{Binding CONAME}"`. Its own colors: `row.CONAME.Foreground` / `.Background` (over the row colors; frozen brushes, set after the text, because assigning a string creates a new cell). The GTN cell style switches `UIXDataGridCellColors.IsEnabled` on: the engine then binds the colors of the `UIXDataGridCell` of the column to the `DataGridCell` (every bound column, template columns via `SortMemberPath`), and the style draws them. Engine hooks on cells use instance handlers: WPF raises `Loaded` only on elements with an own handler, a class handler (`EventManager.RegisterClassHandler`) is skipped.
- **Codetable keys** are compared directly as string literals (e.g. `t1profi.LNTY == "STEAM"`); don't create an enum or constant class per codetable entry.
- **Culture:** data (SQLite, CSV, files, IDs) uses `InvariantCulture`, the UI uses `CurrentCulture` explicitly; CA1304/CA1305 are build errors. All value conversions go through `UIXSqliteDataType.Convert` (C# / SQLite / CSV / UI). Numbers typed into the UI are parsed with `ConversionType.UI` (strict, current culture, no thousands separators) — never with `double.TryParse` and friends directly. Numeric TextBoxes bound via `UIXAttachedProperty.Path`, `FnControls.ContainsOnlyNumericValue` and `FnConvert.ToDouble` already use it.

## Architecture

### Layout
- `GameTimeNext/Core/Framework/` — app-wide infrastructure: `AppEnvironment` (global service locator: config, DB manager, current profile, background processes, started apps), `ApplicationLauncher` (opens apps as tabs), `Config/`, `DataBase/`, external integrations (`SteamGridDB`, `Igdb`/Twitch, `GitHub` version check, `LauncherIntegration`), `Utils/` (`Fn*` static helpers).
- `GameTimeNext/Core/Application/<Module>/` — one folder per feature module (Profiles, Playthroughs, Dashboard, Codetables, Settings, Metadata, …).
- `devsync/` — CSV snapshots of dev-synced tables (codetables, metadata) committed to the repo.

### Modules ("applications")
Each module is a `UIXApplication` subclass (`<Name>App.cs`) that creates its views in `InitializeApplicationOutput()` and wires each view to a controller. It holds the table objects being edited (e.g. `PlaythroughEditApp.T1plthr`) and exposes entry methods like `Edit(...)` / `CreateNew(...)` that take a result callback. Modules implementing `IUIXApplicationStarter` can be hosted in a tab; `ApplicationLauncher.LaunchApplication` instantiates them by type name via reflection. Which modules the user can open comes from the menus (module "Menus", table `T1MENUE`: folders `METY = "01"` and application calls `METY = "02"` with `MEAP` = APDID / class name, resolved by `FnApplications.ResolveApplicationType`); the application search (Ctrl+M) shows them as a tree. Only definitions with "Menu call possible" (`T1APRDH.APMCP`) can be chosen. Entries marked as dev tool (`T1MENUE.DEVT`, on a folder for everything in it) are only shown in debug / dev mode (`FnSystem.IsDebug() && !FnSystem.RunWithUserPermissions()`). The icon of an application is declared with `[UIXAppIcon(...)]` on its class, so it can be read without creating the application.

Every application (also dialogs, edit apps and background processes) must override `InitializeAppInfo()` and call `ReadFromAppProperties(nameof(<ClassName>))` there; it runs in the constructor before `InitializeApplicationOutput()`. The properties (`AppProperties`: `ApplicationName`, `ApplicationDescription`, `ApplicationHelpText` as Markdown, `IsMenuCallPossible`) are maintained in the module "Application Properties Definition" (table `T1APRDH`, ID = class name). The engine only knows `IUIXAppPropertiesProvider`; GameTimeNext registers `Core/Framework/AppPropertiesProvider.cs` in `App.xaml.cs` after `AppEnvironment.Initalize()`. Applications created before that, or without a definition, get properties that only contain their name.

Error messages work the same way: they are maintained in the module "Errormessages" (table `T1ERMSG`, key = message number `ERMNR`, text `ERMSG`, hint `ERHIN`). The engine only knows `IUIXErrorMessageProvider`; GameTimeNext registers `Core/Framework/ErrorMessageProvider.cs` as `UIXApplication.ErrorMessageProvider` in `App.xaml.cs` after `AppEnvironment.Initalize()`. Call `GetErrorMessage("<number>", p1, p2, ...)` on the application object (instance method of `UIXApplication`; in controllers the shortcut `GetErrorMessage(...)` delegates to `App`, e.g. for `AddViewError`); placeholders `&1`, `&2`, ... are replaced with the parameters in order (current culture) and a typed `\n` becomes a line break, `GetErrorMessageHint` does the same for the hint. An unknown number returns a fallback text and logs a warning.

Logging works the same way: `FnLog.AddInfo` / `AddWarning` / `AddError` (engine) only build a `UIXLogEntry` and pass it to `FnLog.LogProvider` (`IUIXLogProvider`); where it ends up is decided by the host. GameTimeNext registers `Core/Framework/LogProvider.cs` as the first step of `InitializeApp` in `App.xaml.cs`; new log targets are added there, not in the engine or at the call sites. It writes into table `T1SYLOG` of the log database; the text file `AppConfig.LogFilePath` (engine `UIXFileLogProvider`) is the fallback: until `App` sets `StartupCompleted` (after the main window is started) every entry is also written to the file, because if the app doesn't start, the module "Diagnostics" can't be opened; afterwards only when the log database can't be written (the reason is written once into the file). Without a provider the engine logs to the debug output; `FnLog.Configure(path)` sets a `UIXFileLogProvider`. An exception of the provider never reaches the caller (written to the debug output instead). **Log source** (first parameter of `FnLog.Add*`) is always an application: `GetApp()` in controllers and selector parts (never `this` of a controller or a view), `App` in engine controllers, `this` only inside an application class; a class that logs without being one gets the application passed in (e.g. `GamepadInput`, `CodeGenerator.GenerateFor(app, ...)`), engine controls find it with `UIXApplication.FindFor(element)`. Every entry carries the place of the call (`UIXLogEntry.Caller`, from caller attributes: never pass `callerMember` / `callerFile` / `callerLine`) and the call stack (`StackTrace`, also for infos; `FnLog.CaptureStackTrace`), stored in `T1SYLOG.LGCL` / `LGST` (the text log only gets the caller); an own log helper that wraps `FnLog` forwards the caller parameters and is marked `[StackTraceHidden]` (see `MigrationFactory.LogInfo`). Exceptions: static `Fn*` / `CF*` helpers log with their own name (`nameof(FnLauncher)`, integrations behind a facade with the facade's name), and code that runs before or after any application (`App.xaml.cs`, startup migrations, app-wide background / cover helpers) logs as `"MainApp"`. Log types are `UIXLogType` (a class, not an enum: `Info`, `Warning`, `Error`); own types go into a subclass with static fields (`public static readonly GTNLogType Debug = new GTNLogType(nameof(Debug));`, protected constructor) and are logged with `FnLog.Add(type, ...)`. The key (`UIXLogType.Key`, stored in `T1SYLOG.LGTY`) is by convention the field name, so `nameof(UIXLogType.Error)` serves as constant in `switch` and codetable keys. The separate log database (`AppConfig.LogDatabaseFilePath`, in the logs folder) is opened by `LogDataBaseManager` (`AppEnvironment.GetLogDataBaseManager()`): initialized before the provider is set and closed as the very last step of `OnExit`. Its table `T1SYLOG` is created by the manager itself with plain SQL (`CREATE TABLE IF NOT EXISTS`), not through metadata, and is accessed with SQL, not table objects. Every access to its connection is done inside `lock (SyncRoot)` (entries come from several threads), and nothing in it may log through `FnLog` (the provider writes into it, so it would recurse).

Inside a module:
- `Views/` — XAML views; `Controller/` — `UIXViewControllerBase` subclasses; `ViewModel(s)/` — WPF view models.
- **Selectors** (`Selectors/` folder of the module): every list control of a view (`UIXDataGrid` / `UIXTreeGrid`, `UIXListBox`, `UIXListView`, ...) is built by a selector adapter and its events are handled by a selector controller, not by the view controller. Both are assigned in the application right after creating the view, like the view controller: `CodetablesView.DgCodetables.SelectorAdapter = new CodetablesView_CodetablesSelectorAdapter(this);` / `.SelectorController = new ...SelectorController(this);` (engine `IUIXSelector`). Every list always gets both classes, also a selector controller without handlers yet, so its events have a fixed place.
  - **Adapter** (`UIXSelectorAdapterBase<TApp, TView, TSelector, TItem>`): `ExecuteAsync(CancellationToken)` returns the items (list entry view models / rows), always async: it runs on the UI thread, reads the filter controls there and moves queries into `Task.Run`. The base sets them as `ItemsSource` (`ObservableCollection<TItem>`); override `SetItemsAsync` to add them step by step (profile tiles). Rows are created with `GetSelector().CreateNewRow<...>()`. State the list depends on comes from the app or the view controller (`GetViewController<T>()`); state the view sets on the adapter (e.g. the page shown) via `control.GetSelectorAdapter<T>()`.
  - **Loading:** the view controller (or the selector controller) only calls `await GetView().dgXxx.LoadDataAsync()` (extension in `FrameworkElements/Selectors`); it shows the loader (`App.Loader`) while `ExecuteAsync` runs. A newer call cancels a running one (token): it returns false then and its items are not set, so code after it (selecting a row, counts, empty state) runs only `if (await ...LoadDataAsync())`. Errors of `ExecuteAsync` are passed on to the caller. No own `Loader.Begin/Stop` around a list build. Every view controller whose view shows the loader sets its own loader texts in `Init` (`GetApp().Loader.SetRandomTexts(...)`, a handful of playful English lines about its module; no app name literal, see `cleancode.py`); selector controllers use the texts of their view. The texts belong to the application: the overlay of a window is shared, but every application holds its own handle on it (`UIXApplication.Loader` creates one when it is set, `UIXLoader.CreateHandle`), and a load shows the texts of the application that started it. Views that pass a fixed text to `Loader.Begin(text)` need none.
  - **Selector controller** (`UIXSelectorControllerBase<TApp, TView, TSelector>`): handlers without the control's name, because the controller belongs to one control: `EV_SelectionChanged`, `EV_CtxtOpening(FrameworkElement item)`, `EV_DragAndDrop(UIXDragAndDropArgs)` (switches on reordering, same rules as `EV_<name>_DragAndDrop`), `EV_<menu item name>` for the context menus of its items (e.g. `EV_ctxtDelete`; double click / Del run them as before) and `EV_<button name>(FrameworkElement item)` for named buttons inside an item (e.g. in a cell template). Menu items and buttons without a handler there go to the view controller; the view controller's pipeline (`TriggeredEvent`, `Check`, DataWrapper of a combined edit) still runs. `GetSelectedItem<TItem>()` gives the selected entry; functions of the view (e.g. opening an entry in the edit area of a combined edit) are public methods of the view controller, called with `GetViewController<T>()`.
  - **Names:** `<ViewName>_<Content>SelectorAdapter` / `<ViewName>_<Content>SelectorController` with the full view name (e.g. `ProfilesEditView_PlaythroughsSelectorAdapter`); `<Content>` is what the list shows, or its purpose when two lists of a view show the same (e.g. `ProfilesView_FavoriteProfilesSelectorAdapter`). A view can have several selectors. Selectors are never shared between views: each view builds its own lists.
  - **Selector controls are always the engine's UIX classes** (`UIXDataGrid`, `UIXTreeGrid`, `UIXListBox`, `UIXListView`, `UIXTabControl`, `UIXComboBox`), never plain `DataGrid` / `ListBox` / `ListView` / `TabControl` / `ComboBox`; `Scripts/cleancode.py` checks the XAML. Implicit styles only apply to the exact type, so a new UIX class needs its own implicit style `BasedOn` the WPF one (see `UIXListView` in `ListViewStyle.xaml`, `UIXTabControl` in `TabControlStyle.xaml`).
- Controllers derive from the generic bases `UIXViewControllerBase<TApp, TView>` (views) / `UIXWindowControllerBase<TApp, TView>` (`UIXWindowBase` windows), e.g. `class ProfilesEditViewController : UIXViewControllerBase<ProfilesEditApp, ProfilesEditView>`, and use their `GetApp()` / `GetView()` (`GetView()` also returns the window of a window controller; there is no `GetWnd()` / `GetWindow()`). Don't write own casts of `App` / `View`. A controller can't be more visible than its app and view types (an `internal` app needs an `internal` controller).
- Controllers follow a fixed lifecycle of overrides: `Init`, `BuildFirstImpl`, `BuildImpl`, `FillViewImpl`, `CheckImpl`, `FillDBOImpl`, `SaveDBOImpl`, `UnsavedChangesImpl`, `TriggeredEvent`, `DataWrapperSelectionChangedImpl`. `Init` registers data sources/identifiers (`AddSource`, `AddIdentifier("T1XXXXX", obj)`). The engine loads the contents of all tabs of a view once (per reset) right before `BuildFirst` (forced layout of every tab, so their controls exist for mapping / validation), so lists filled in `BuildFirstImplAsync` are not laid out on tabs that are not shown. Validation reports errors via `AddViewError`. Results are returned through a nested `UIXViewReturn` subclass.
- **Unsaved changes:** the engine remembers the values of the bound controls (`UIXAttachedProperty.Path`) and the state of the table objects after opening and after saving; `HasUnsavedChanges()` compares against them. When the user closes a view with unsaved changes (cancel button `btnCancel` / Esc, closing its window, closing its tab or the program), the engine calls the abstract `UnsavedChangesImpl(UIXUnsavedChangesArgs args)`; every controller implements it. Views with a save button call `CFMBOX.AskUnsavedChanges(GetApp(), args)` there (message `GLO0022`: Yes = `args.Save`, saves like `btnSave` and closes only if saving succeeded; No = discard; Cancel = `args.Cancel`, stays open); all others leave the body empty (= close without asking). A close by the controller itself (`Exit`, e.g. after saving) never asks, and neither does `Application.Shutdown` (e.g. restart), because WPF ignores a cancel there. Not detected: values the controller reads from unbound controls (e.g. the profile settings in `PRSE`). A controller that saves one of its table objects itself (outside `SaveDBO`, e.g. the metadata header's `GENER`) calls `AcceptTableObjectsAsSaved()` afterwards, otherwise closing the view asks about a change that is already saved.
- **Event handlers are bound by reflection, by naming convention.** A method named `EV_<x:Name>` (e.g. `EV_btnSave`) handles that control's event, and `EV_<name>_CtxtOpening` handles its context menu opening. `EV_<name>_DragAndDrop` (optional parameter `UIXDragAndDropArgs`: item, old / new index) switches on reordering the items of that list control by dragging (only `DataGrid` without `UIXTreeGrid`, `ListBox` / `ListView` and `TabControl`, with a `StackPanel` / `VirtualizingStackPanel` as items panel, not sorted / filtered / grouped, `ItemsSource` a changeable `IList`; anything else stays off or is refused with a warning in the log) (engine `AttachedProperties/UIXDragAndDrop.cs`) and is called after a drop, when the order of the `ItemsSource` (or `Items`) is already changed; never wire drag and drop with own event handlers. Renaming a control in XAML silently breaks its handler. The events of a list control with a selector controller go to that controller instead (see Selectors).
- Views bind controls to table fields with `uixprops:UIXAttachedProperty.Path="T1PLTHR.PTDE"`; the framework moves values between view and object. A bound control that is not `Visible` writes the field's default value on `FillDBO` (unless `UIXAttachedProperty.SkipNotVisible="True"`), so never keep a hidden control just to carry a value: set the field on the table object in the controller instead.
- `ViewIndicator` encodes the view mode: `CN` = create new, `ED` = edit, `SE` = select.
- `CF<Name>App.cs` — static helper functions for a module (formatting, dialogs, etc.).
- **Combined edit (CE):** an overview with an edit area next to the list (e.g. Menus, Application Properties Definitions). The list (source) and the edit view (target, a `UIXUserControlBase` in a `ContentPresenter` of the overview) share a `UIXCE_DataWrapperBase<TDataSource, TData>` that holds the edited object (`Get()` / `Set()` / `HasData`). Selecting a row opens it in the edit area; new entries are opened unsaved via `Set()` + `TargetController.Open(true)`. After Save or Cancel (Cancel is called "Discard" for a new, unsaved entry) the edit area always closes and no row is selected. The overview needs a ViewIndicator (`ED`), otherwise its controller protects the mapped fields of the embedded edit area. The list is built like in every other overview: by its selector adapter, async with the loader; the view controller keeps the public functions of the edit area (e.g. `OpenInDetail`, `CloseDetail`, rebuild and select) that the selector controller calls.

### UI conventions
- **View margins:** the main window's tab content area (`ModernTabControlStyle`) insets every view by 12 px, aligned with the tab bar. Root grids of views use `Style="{StaticResource View.Root}"` (`UI/Styles/Views/WindowStyle.xaml`) instead of their own outer margin: no margin inside a tab, `20,16,20,20` when the same view is opened in its own window. This works via the inherited attached property `ViewHost.IsTabContent`, set by the tab control.
- **Toolbars** (search fields, filters, action buttons above a list) sit in a `Card` border with `Padding="16"`.
- **Typography:** use the type ramp in `UI/Styles/Controls/TextBlockStyle.xaml` (`Text.Display` 28, `Text.Title` 20, `Text.Subtitle` 16, `Text.BodyStrong` / `Text.Body` 14, `Text.Label`, `Text.Hint` 13, `Text.Caption` 12, `Text.Icon`) instead of ad-hoc font sizes. The implicit TextBlock style sets no weight: body text is normal, only headings, values and buttons are SemiBold (no `Bold`). Labels in front of inputs use `Text.Label` (muted color), never white text with `Opacity`; explanations below a setting use `Text.Hint`. Control templates that show string content (tab headers, buttons) define a local TextBlock style in `ControlTemplate.Resources`, otherwise the implicit style pins the text to white and the template's foreground states don't apply.
- **Icons:** always `FontFamily="{StaticResource Font.Icons}"` (Segoe Fluent Icons, MDL2 fallback; `UI/Values/UIValues.xaml`), 14 px in icon buttons; no emoji as icons. Icon-only buttons need a `ToolTip`.
- **Spacing:** 4 px grid (4 / 8 / 12 / 16 / 24); 12 between label and input, 8 between buttons, 16 between cards and sections.
- **Primary action:** the confirming button of a view or dialog (Save, Apply, Import, Select, ...) uses `Button.Primary`; Cancel / secondary actions stay neutral. CFMBOX highlights its default button itself. A question that needs a typed answer uses `CFMBOX.ShowInput(message, defaultText)` (input field with OK / Cancel; result `CFMBOXInputResult` with `IsConfirmed` and `Text`; always the dialog window, also in the Big Picture mode).
- **Save confirmation:** after a successful save via `btnSave` (click, Ctrl+S, "Yes" on the unsaved changes question) the engine sets `UIXSaveFeedback.IsSaved` on the button (engine `AttachedProperties/UIXSaveFeedback.cs`) and waits `WaitTime` before `EV_btnSave` runs, so the check is seen before the view closes. The look (text fades out, a filled circle scales in and a check is drawn in it) is a trigger in `Template.Button` (`ButtonStyle.xaml`); `WaitTime` / `ShowTime` are set in the implicit Button style. Nothing to do in the modules; don't add own save animations.
- **Trigger animations:** storyboards started by template/style triggers are layered by the order of the triggers, not by start time: a later declared trigger's held animation wins. Don't split open / close of one property into separate triggers; use one trigger with Enter/ExitActions (combine conditions with a MultiBinding, e.g. `AnyTrueConverter` for OR; see the game cases in `TileViewStyle.xaml`).
- **Big Picture mode** keeps its own look (`BigPicture.*` styles); app-wide style changes must not alter it.
- **Layout logic goes into attached properties in `Core/Framework/UI/`, not into code-behind**, e.g. `ClipBehaviors.CornerRadius` (rounded clip that follows the size), `ScrollFade.Length` (fades scrolled content at the top/bottom edge while more content is beyond it), `TileLayout.AutoSize`, `TextBoxBehaviors`, `ViewScale.DesignHeight` (lays a view out for a fixed height and scales it to its container, for TV views), `BringIntoViewBehaviors.When` (scrolls an item into view when a bound flag such as `IsSelected` turns true).
- **Accent colors** are profile dependent (`FnTheme.ApplyProfileAccentColors`, falls back to the default accent from `UI/Colors/Colors.xaml`). A `{DynamicResource Color.Accent*}` inside a brush defined in a ResourceDictionary does not follow runtime changes (shared resource, resolved once): either reference `Color.Accent*` directly in the element/template, or register the brush in `FnTheme.AccentResources` and reference it with `DynamicResource` only (FnTheme replaces the instance; a `StaticResource` keeps the old, frozen one — this is what made hover outlines show a previous profile's color). Neutral hover/selection surfaces use `Brush.Item.Hover` / `Brush.Item.Selected` (white glass, not accent tinted).
- **Sub windows are not resizable**: `GTNWindowView.ResizeMode` defaults to `NoResize`; give a view a fixed `Width`/`Height` that fits its content. Only a deliberate exception sets `ResizeMode="CanResize"`. Sub windows can't be moved or resized beyond the main window (`UIXWindowBase` in the engine).
- **Windows are hosted by the UIX view** (`UIXWindowHost`, engine `FrameworkElements/Windows/`): an application whose main view (`UIXUserControlBase`) is shown embedded in a `ContentPresenter` (a tab, the Big Picture presenter, ...) gets that view as `UIXApplication.WindowHost`, and every application created from it with `GetApplication` inherits it (also from inside one of its windows, so a window opened from a window is not caught in that window). Hosted windows open centered in the view, can only be moved within it, follow it when the main window moves, are cloaked via DWM while the view is not visible (e.g. another tab is selected; they stay shown for WPF, so controllers see no visibility change and they reappear without a white flash; a window opened meanwhile appears when the view is shown again) and closed when the view is closed or the application is closed with `UIXApplication.TryCloseViews()` (asks about unsaved changes and returns false if the user keeps something open; `ApplicationLauncher.CloseApplication` calls it for a closed tab and then keeps the tab; a hidden view can't be told apart from a removed one by its trees, so whoever removes a hosted view without closing it calls it). `UIXWindowHost.BringIntoViewHandler` (set by `ApplicationLauncher`: selects the tab) shows a hidden view before a question is asked in it. `Dialog = true` is only modal to the view (it blocks the view and its other windows: a transparent adorner over the view takes all mouse input, so there's no hover or tooltip either, and the keyboard is blocked; the rest of the app, e.g. other tabs, stays usable) and still returns when the window is closed, so callers stay synchronous. Applications without a host (e.g. `MainApp`, `new CFMBOX()`) open windows as before, modal to the whole app. Nothing to do in the modules; to host windows in another element, assign `UIXWindowHost.GetOrCreate(element)` to `WindowHost`. Limitation (one UI thread, nested dispatcher frames): if view A waits for a modal result and a modal is opened later in view B, A's code after the call continues only once B's modal is closed (result callbacks of edit apps fire immediately, only code after `Show`/`CFMBOX.Show` waits).
- **Context menus** all share one look (the glass `ModernContextMenuStyle`, `UI/Styles/Controls/ContextMenuStyles.xaml`): it is the implicit default for every `ContextMenu` and pins its own TextBlock/MenuItem/Separator styles, so local styles of the hosting control (e.g. the DataGrid's TextBlock style) don't change it. Don't give context menus their own styles.
- **ComboBoxes** are `uixcb:UIXComboBox` (engine `FrameworkElements/ComboBoxes/`), filled either from a source (`UIXAttachedProperty.Source="From=...;Text=...;Value=..."`) or, when filled in code, always with `UIXManualCodetable` (`AddEntry(key, text)`, `ApplyTo(cmb)`); never add `ComboBoxItem`s by hand or in XAML. The entry without key ("(None)", "(All)", ...) is the property `AdditionalEntry` of the `UIXComboBox`, set once in XAML (in code only when it depends on data, before `ApplyTo`). Both ways create `ComboBoxItem`s with the key in `Tag` (`UIXComboBox` defaults `SelectedValuePath` to `"Tag"`, so `SelectedValue` is the key) and a `UIXComboBoxEntry` as content, which the implicit DataTemplate in `UI/Styles/Controls/ComboBoxStyles.xaml` shows as key badge plus text (drop down and selection box). Only for technical keys that mean nothing to the user (device IDs, internal constants, index based choices) and for lists that are no codetable (e.g. the application search in the title bar, `PART_ApplicationSearchBox`) set `ShowKeys="False"` on the `UIXComboBox`.
- **Date inputs** are the plain WPF `DatePicker` (no engine class needed; `UIXAttachedProperty.Path` / `UIXControlValueHelper` read and write `SelectedDate`). Its look (field like TextBox / ComboBox, drop down calendar on the popup surface) is the implicit style in `UI/Styles/Controls/DatePickerStyle.xaml`, which also styles `Calendar`; don't give DatePickers their own styles. A date range filter takes whole days: from the start of the From day, to the end of the To day (exclusive next day).
- **Splitters** between two areas (e.g. list and detail) are a plain `GridSplitter` in its own 16 px column (the gap between cards); the implicit style in `UI/Styles/Controls/GridSplitterStyle.xaml` draws a fine line that turns accent on hover / drag (`GridSplitter.Horizontal` for one between rows). A detail column that closes while nothing is selected gets the width 0 (with its splitter column) instead of only a collapsed presenter, and keeps its last width for the next opening (see `DiagnosticsViewController.SetLogDetailOpen`).
- **Markdown fields** (long text, type `07`) use `uixmd:UIXMarkdownEditor` from the engine (`FrameworkElements/Markdown/`): a TextBox with Edit/Preview switch, bound with `UIXAttachedProperty.Path` like any TextBox. Pasted, dropped or inserted images are scaled down (`MaxImageWidth`/`MaxImageHeight`, default 800 px) and embedded into the text as reference definitions with a data URI (`[img-1]: data:image/...;base64,...`) at the end. The engine control holds the behavior; its look is the implicit style in `UI/Styles/Controls/MarkdownEditorStyle.xaml`.
- **New UIs keep the GTN look:** when a screen is inspired by another product (e.g. the Big Picture mode by console dashboards), take over the idea / arrangement only, never its look 1:1: GTN card glass (`Brush.Card.*`), accent selection, the tab bar, `Control`/`Card` corner radii. Modern and calm; no heavy 3D effects (subtle light and a fine edge at most).
- Spacing that must scroll with the content belongs on the items panel (e.g. `WrapPanel Margin`), not on `ListBox.Padding`: the default template applies the padding outside the scrolled area and shrinks the viewport.

### Data layer (SQLite)
Tables use 7-char names (`T1` prefix + 5 chars, e.g. `T1PROFI`, `T1PLTHR`, `T1SESSI`, `T1CTABH/D`, `T1METAH/P`), with a prefix per class role, and columns use 4-char codes. For table `T1SESSI`:
- `TableObjects/T1SESSI.cs` — generated row object (`UIXTableObjectBase`) with change tracking (`HasChanged`, `AcceptChanges`, `State`), uppercase column properties marked `[UIXSignatureField(n)]`.
- `TableObjects/K1SESSI.cs` — generated constants for table and field names; use these with `UIXQuery` instead of string literals.
- `DataManagers/TXSESSIBasic.cs` — generated CRUD (`CreateNew`, `Read`, `Save`, `Delete`, …).
- `DataManagers/TXSESSI.cs` — subclass of `TX…Basic`; the generator only creates an empty template and never overwrites it. It holds **CRUD functions only** (e.g. `TXSCRSP.DeleteAllWhereSSID`).
- `DataManagers/TFSESSI.cs` — hand-written static query/business functions for the table (e.g. `TFPLTHR.GetCurrentPlaythrough`). Anything beyond CRUD goes here, not into `TX…`.

**Never hand-edit `T1…`, `K1…` and `TX…Basic`** (also the metadata tables' classes in `Core/Application/Metadata/Data/`): the developer regenerates them through GTN (Metadata module / code generator). If one of them needs a change, change the metadata or the generator and regenerate.

Schema is metadata-driven: table definitions live in metadata tables `T1METAH` (header) / `T1METAP` (positions), editable in the Metadata module. `MigrationFactory.Metadata.CodeGenerator.GenerateFor(T1METAH)` generates the T1/K1/TXBasic/TX classes; if a file with that name already exists in the solution it is overwritten in place (except `TX*.cs`), otherwise it is written to `%LOCALAPPDATA%/<Publisher>/GameTimeNext/dev/genClass/`.

The metadata tables themselves are not rows in `T1METAH`/`T1METAP`; their schema is hard-coded in `MigrationFactory.Metadata.METADATA`. `CodeGenerator.GenerateForMetadata()` (button "Generate classes of the metadata tables" in the Metadata view) generates their classes from that definition into `Core/Application/Metadata/Data/`, following the same T1/K1/TXBasic/TX pattern. To change a metadata table, edit `METADATA`, then regenerate. Generated `TX*Basic` classes take an optional `SQLiteConnection` in the constructor (used when migrating into another database), and set `CRUS`/`CHUS` on insert/update when the table has those fields.

`MigrationFactory` (`Core/Framework/DataBase/Migration/`, partial class split by concern) handles schema diff/migration from metadata, CSV import/export (`ToCsv`/`FromCsv`), and import packages.

### DevSync (debug only)
For tables marked as dev-synced in metadata (`IsDevSynced`), saving a table object in debug re-exports its CSV into `devsync/<TABLE>.csv`, and on startup `MigrationFactory.FromCsv.MigrateTables(ImportType.DevSync)` re-imports these CSVs. `ImportType.DevSync` and `MetadataGenerator` only run when `FnSystem.IsDebug()` is true (a DEBUG build plus an attached debugger or a running `devenv`). This keeps reference data (codetables, metadata) in sync across developers through git, so the CSVs under `devsync/` are source-controlled data, not throwaway output.

### Startup & versioned migrations
`App.xaml.cs` `OnStartup`: single-instance check → parse start args into `AppEnvironment.StartArguments` → file-system migration → load `AppConfig` → init logging (`FnLog`) and `DataBaseManager` → `AppEnvironment.Initalize()` → start `MainApp`.

`AppEnvironment.Initalize()` order: backup → `MigrationFactory.Metadata.MigrateTables()` (schema from metadata) → changelog → import packages → DevSync CSV import (debug only) → `MigrationManager.Migrate()` → seed `T1GROUP`.

Version-specific data migrations are `MigTask_<version>_<seq>` classes (subclassing `MigTaskBase`) registered in order in `MigrationTasks/MigrationManager.Migrate()`.

### Launcher integration
A profile is linked with a launcher by `T1PROFI.LNTY` (launcher type, key of codetable `lT`) and `T1PROFI.LNID` (game ID in that launcher: Steam app ID, file path for `LINK`, ...); launch arguments are `CProfileSettings.LaunchArgs` in `PRSE`. Each launcher is an `ILauncherIntegration` (`Core/Framework/LauncherIntegration/<Launcher>/`, based on `LauncherIntegrationBase`) that returns its codetable key in `LauncherType` and declares its features (`SupportsImport`, `SupportsLaunchArguments`, `SupportsOpenInLauncher`); new launchers are registered in `LauncherRegistry`. Modules only use the facade `FnLauncher` (link/unlink, installed games of all launchers, start with profile settings such as HDR, cancel the launch, quit the running game, open in library) and adapt their UI to the features, never to a specific launcher. Running game detection (`GameRunningProcess`) doesn't depend on the launcher, it uses `EXGF`/`EXEC`. `T1PROFI.SAID` is legacy: `MigTask_100b_010` moves it to `LNTY`/`LNID`.

### External APIs
SteamGridDB and IGDB (with its Twitch authentication) are called through `HttpClient`s whose handler comes from `FnApiStatus.CreateHandler(FnApiStatus.SteamGridDB / Igdb[, innerHandler])` (`Core/Framework/Http/`): `ApiStatusHandler` counts every request (time, duration, HTTP status, errors) in `FnApiStatus`, which the module "Diagnostics" shows in its tab "Status" below the background processes together with the configuration from the settings. A new client of an external API (or a new API, added to the list in `FnApiStatus`) gets its handler the same way, otherwise its requests are missing there. On every load of that list (open, refresh) each configured API is checked with a small test request (`SteamGridDBClient.CheckConnectionAsync`, `IgdbService.CheckConnectionAsync`, run by `FnApiStatus.CheckAsync` with a timeout; result in `ApiStatus.LastCheckAt` / `LastCheckError`), so its status is the current one; a new API gets such a check too.

### Big Picture mode
`Core/Application/BigPicture/` is the full screen library for TV and game controller. It is not a tab: `MainWindowController.EnterBigPicture` sets `GTNWindow.IsFullScreen` (no title bar; a normal, non-resizable window placed exactly over the monitor, because Windows maximizes a resizable window only to the work area) and starts `BigPictureApp` into the `cpBigPicture` presenter over the tabs; `EXEV_ExitBigPicture` closes it. Opened by the title bar button (`btnBigPicture`, `ShowBigPictureButton`) or the start argument `--bigpicture`. While it is open, the main window's keyboard goes to it (`HandleGlobalShortcut`), and `GamepadInput` (`Core/Framework/UserInput/`, XInput) is polled; when another window of the app is active (e.g. a CFMBOX), controller buttons are sent there as keys (`FnKeyboard`). It starts `ProfilesApp` if needed, because the running game detection depends on it, and `GameRunningProcess` reports starts/ends to it via `EXEV_BigPictureGameLaunched` / `EXEV_BigPictureGameClosed` (only triggered while registered). Layout: pivots Home / Library / Search (GTN tab bar look, LB / RB), each a row of covers with the selected game large below it (name, times, current non-initial playthrough, play) and its cover as key art; it must keep the GTN look (card glass, accent selection), not copy console UIs. The on-screen keyboard is a `Canvas` of `BigPictureKeyTile` entries placed by the controller, navigated by position. Selection is a controller model (`IsSelected` on the entries), not keyboard focus, so buttons in the view are `Focusable="False"`. The controller is split into partial files by concern (games, launch, menu, search, filter, monitoring). Opening plays `CFParticleIntro` (`Core/Framework/UI/`) over it. Controller buttons: A play / back to the running game, X game menu (monitoring, quit), View blackout (`CFBlackout`), keyboard: Enter = A, Esc = B, Tab = X, F3 = Y, F5 = View, Page Up / Down = LB / RB; Guide or View + Menu back to the running game (`FnLauncher.SwitchToGame`); after such a return the mode also takes controller input while it is visibly on top without the focus (`FnForeground.IsVisibleOnTop`), because Windows doesn't always hand over the focus. While the mode is open it is `CFMBOX.Presenter` (`ICFMBOXPresenter`): Default/Memotext message boxes are shown in its own dialog and `CFMBOX.Show` waits in a nested dispatcher frame; Markdown messages keep their window. Its library filter is `AppConfig.BigPictureFilterCache`, evaluated by `TFPROFI.GetFilteredProfiles` like the profiles view. While a game is in the foreground, the Xbox button (read via `XInputGetStateEx`, ordinal 100) or View+Menu brings the mode back (`FnForeground.BringToFront`); the game window is minimized first (`FnLauncher.MinimizeGame`), otherwise the game may keep the focus and react to the controller while the mode is operated. Game windows are found with `FnLauncher.FindGameWindow` (largest top level window of the game's executables, also when minimized), not `Process.MainWindowHandle`. For 90 s after the game window appeared (slow computers show it long after the process started; given up after 3 min without a window), the game window is brought in front of the mode whenever the mode is in front instead (games starting in a window don't get the focus from Windows); the result is logged with the foreground window (`FnForeground.DescribeForegroundWindow`). A game that has the focus but lies behind the mode in the z-order (seen with Portal / Source games switching to full screen) is raised (`FnForeground.Raise`); if it stays covered, the mode is moved behind it (`FnForeground.Lower`). Main menu: "Screen setup" applies a screensetup (`CFScreensetupsApp.ApplyScreensetupAsync`) and moves the mode to the new primary monitor (`GTNWindow.MoveFullScreenToPrimaryMonitor`; full screen also refits itself on `WM_DISPLAYCHANGE`); "Minimize" is the way out when a window is hidden behind the mode. While a game is launched, the mode is `Topmost` (launch cover, `CoverLaunch`) so launcher, splash and console windows stay behind its launch card; it is lifted as soon as `FnLauncher.FindGameWindow` finds the game window (which is then brought to the front), when a foreign window keeps the foreground for 4 s (a launcher dialog waiting for input) or after 45 s. The hints, the button glyphs of the view (`cc*` controls, set by `ApplyButtonLabels`) and texts naming a button follow the input device last used (`BigPictureInputDevice`: keyboard / mouse, Xbox, PlayStation); labels and colors come from `CFBigPictureApp.GetButtonLabel` / `GetButtonBrushKey`, never write a button name like "X" into a text directly. PlayStation controllers (DualShock 4, DualSense; `FnGamepadDevices`) are read directly over HID by `PlayStationControllers` (USB and Bluetooth report layouts), because Steam Input feeds its virtual Xbox controller only while a Steam game is in front; `GamepadInput` merges them with XInput as a union per poll, so a button reported by both counts once. A controller opened exclusively by another program (DS4Windows with HidHide) is left to XInput. While the mode is open, `CFBigPictureApp.IsOpen` is true: other modules leave out toasts that would pop up in front of the game. Performance: WPF also renders covered elements, so `MainTabControl` is `Hidden` while the mode is open; no live `BlurEffect`/`DropShadowEffect` on large or many elements (backdrop and key art are pre-blurred once per cover by `CFBigPictureApp.CreateBackdrop` / `CreateKeyArt`, the cover glow is collapsed unless selected); `GamepadInput` polls XInput on its own thread and raises its events on the UI dispatcher. Pausing: XInput is global, so a game in the background keeps reading the controller; when the mode is brought back from a game (`ReturnFromGame`), the game's processes are suspended (`FnLauncher.PauseGame`, `FnProcessSuspension`) if `CProfileSettings.PauseInBigPicture` is on (default true; checkbox in the profile's launch settings, toggled in the game menu X). Every way back to the game or out of the mode resumes it (`FnLauncher.ResumePausedGame`: `SwitchToGame`, `QuitGame`, "Minimize", leaving the mode, the main window losing the focus to another application, game end, `App.OnExit`, unhandled exceptions); never add a path where a paused game could stay suspended. Nothing may wait for a suspended process (its threads handle no messages, the caller hangs): `FnForeground.BringToFront` doesn't `AttachThreadInput` to it (`FnProcessSuspension.IsSuspended`), no `SendMessage` / synchronous `ShowWindow` to its windows; the game is suspended only after the mode is back in front and the game handled the minimizing (`PauseDelay`).

### Runtime
- Background processes: `GameRunningProcess` (polls every 500 ms to detect running game executables and switch profiles) and `GlobalKeyInputProcess` (global hotkeys, e.g. Ctrl+M quick launch). They are stopped on exit, and an auto-backup is created then. `UIXBackgroundProcess` (engine) records runtime statistics (start / stop time, interval, mode, cycle count, last / average / max cycle duration, thread ID); the module "Diagnostics" (`Core/Application/Diagnostics/`) shows them for `AppEnvironment.StartedBackgroundProcesses` (view only) and lists `T1SYLOG` of the log database (`LogDataBaseManager.ReadT1sylog`, newest first).

## Repo conventions

- `.claude/settings.json` denies reading or editing `bin/`, `obj/`, and `.github/`, and denies `git push` and `git reset`.
- Rules agreed with a developer (coding rules, conventions, workflow rules) are always added to this file, in English and in the matching section, so every developer's AI assistant works the same way. Private assistant memory is not enough.
- Commits and branches are done by the developers themselves: do not commit, create branches or offer to do so unless explicitly asked.
- Change only what was asked: when one aspect of a UI element is to be changed, keep its other existing parts instead of removing or replacing them; if something really conflicts, adapt the new part around it or mention the conflict and offer the extra change.
- "Style X like Y" means the visual look of Y (surface, glass, colors, borders), not Y's layout: keep X's own layout and content and put it on Y's surface (e.g. the identify overlay keeps the library's content on the toast glass panel).
